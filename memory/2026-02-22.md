## Bottle Seeker "Zappeln" Bug - Third Fix ✅

**Problem**: Robot still "zappelt" (legs wildly move) when rotating during bottle search, despite previous two fixes.

**Root Cause Identified**: 
- `send_goal_async()` returns immediately and calls callback when **goal is ACCEPTED**
- Callback was NOT waiting for action **RESULT** (completion)
- `action_in_progress` flag reset immediately after goal acceptance
- control_loop (10Hz) could spam new commands while previous action still running
- This caused rapid-fire action spam → robot leg "zappeln"

**Previous Fixes (2026-02-21)**:
1. ❌ First fix: Added `action_in_progress` flag checks
2. ❌ Second fix: Added special search rotation callback, reduced speed/step_size
3. Both fixes still had the fundamental problem: Callbacks triggered on goal acceptance, not completion

**Third Fix Applied** (Commit 576deb0):
```python
# NEW: Two-stage callback pattern
1. send_goal_async() → _on_goal_accepted()
2. _on_goal_accepted() → get_result_async() → _on_action_complete()

# Implementation:
def _on_goal_accepted(self, future, completion_callback):
    goal_handle = future.result()
    if not goal_handle.accepted:
        self.action_in_progress = False
        return
    result_future = goal_handle.get_result_async()  # NOW wait for result!
    result_future.add_done_callback(completion_callback)

def _on_action_complete(self, future):
    result = future.result()  # Result, not GoalHandle!
    self.action_in_progress = False
    self.last_action_time = time.time()
    self.get_logger().info(f'Action complete (success={result.status == 4})')
```

**Changes Applied**:
- Modified ALL action sends to use two-stage callback pattern:
  ```python
  # Before:
  future.add_done_callback(self._on_action_complete)
  
  # After:
  future.add_done_callback(lambda f: self._on_goal_accepted(f, self._on_action_complete))
  ```
- Affected actions:
  - Rotate in SEARCHING state (search rotation)
  - Rotate in CENTERING state (left rotation)
  - Rotate in CENTERING state (right rotation)
  - LinearMove in APPROACHING state
- Added result.status logging (4 = SUCCEEDED per ROS2 action_msgs/GoalStatus)

**Key Insight**:
- ROS2 Actions have TWO async stages:
  1. **Goal Acceptance**: Fast (~instant), just validates goal
  2. **Action Execution**: Slow (seconds), actual robot movement
- Previous code waited for stage 1, new code waits for stage 2
- Only stage 2 completion means robot has actually stopped moving

**Testing**:
- Test script `test_linear_move_action.py` confirmed: Individual actions work fine
- Problem was in bottle_seeker.py control loop logic
- Ready for testing on ubuntu1 with live robot

## ROS2 Workspace Setup on ubuntu1 ✅

**Problem**: Cannot launch from project root, package not found:
```
ubuntu@ubuntu1:~/Hexapod_Brain$ ros2 launch hexapod_navigation bottle_seeker.launch.py
Package 'hexapod_navigation' not found
```

**Root Cause**: 
- ROS2 packages need to be built with `colcon build`
- Workspace needs to be sourced before ROS2 commands work
- ROS_DOMAIN_ID must be set for communication with raspclaws-1

**Solution**: Created `setup_env.bash` script (Commit b28cd56)

**File**: `~/Hexapod_Brain/setup_env.bash`
```bash
#!/bin/bash
# Sets ROS_DOMAIN_ID=1
# Sources /opt/ros/humble/setup.bash
# Sources ~/Hexapod_Brain/install/setup.bash
```

**Usage on ubuntu1**:
```bash
cd ~/Hexapod_Brain
source setup_env.bash  # One-time per terminal session
ros2 launch hexapod_navigation bottle_seeker.launch.py  # Now works!
```

**What it does**:
1. ✅ Built workspace with `colcon build --symlink-install`
2. ✅ Created convenience script that sources everything
3. ✅ Sets ROS_DOMAIN_ID=1 automatically
4. ✅ Shows helpful command examples
